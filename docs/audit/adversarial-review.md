## Finding and disposition

**A1 — current program can remain stale after a future evaluation is cached (high logic, found and repaired during review).** In migration 0025, `private.compute_child_schedule` originally placed current-day `child_programs` reconciliation inside the branch taken only when `schedule_evaluations` inserted a new row. A staff future evaluation could save the next version's snapshot before its effective day. On that day, an identical evaluation reused the saved row through `ON CONFLICT DO NOTHING`, skipped reconciliation, and left the old version assigned. The previously existing T31 test expected a future evaluation to switch today's assignment, which contradicted E04's deliberate current-day rule; its failure could not simply be waived.

The lead moved assignment reconciliation outside the insert-new branch while retaining the child's clinic-local current-day guard. I inspected that SQL and the revised `tests/db/evidence.test.ts` T31 cases. The revised T31 asserts a future v2 evaluation and unchanged current v1 assignment. A separate regression deletes the assignment after an evaluation, then repeats the same current-day evaluation and asserts both evaluation-ID reuse and restored assignment. The lead reports red before the SQL repair and 41 green evidence/schedule tests after it. This is a deterministic test of the cached-row branch, not a real passage-of-time or provider test. The final integrated suite remains the lead's gate.
