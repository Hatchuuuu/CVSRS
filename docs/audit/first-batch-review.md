# Independent first-batch review

Date: 2026-09-30. Read-only review of `0025_scheduling_integrity.sql`, the first API/UI hardening batch, and local destructive test setup. This is code inspection, not a fresh integrated DB run or browser/provider validation.

## Findings

1. **E09 still has one false empty inbox (medium).** [`src/app/messages/page.tsx`](../../src/app/messages/page.tsx) line 19 converts a null `my_messages` result into `{unread: 0, items: []}`. [`0017_certificates_messages.sql`](../../supabase/migrations/0017_certificates_messages.sql) lines 300–302 explicitly return null if `private.session_ok()` is false, including an inactive profile. `get_my_context` still returns that profile, so `requireViewer` can admit the page. The user then sees “No messages yet” rather than an access/unavailable state. Handle null explicitly and test the inactive-profile case.
2. **A test override can erase the reserved local development DB (high reliability).** [`tests/db/global-setup.ts`](../../tests/db/global-setup.ts) forwards `CVSRS_TEST_DB_NAME` to `reset`. [`scripts/db.ts`](../../scripts/db.ts) lines 74–83 accept any `cvsrs_*` name, including `cvsrs_dev`, then run `drop database ... with (force)`. Reserve `cvsrs_dev` and any other non-test names in the reset guard; assert this in a non-destructive unit test. Existing default `cvsrs_test` and the separate audit DB names are safe when used as intended.
3. **`queue_transition` locks before authorization (low security/performance).** [`0025_scheduling_integrity.sql`](../../supabase/migrations/0025_scheduling_integrity.sql) lines 77–83 reads an entry's child and takes a `FOR UPDATE` child lock before calling `queue_transition_prev`, whose capability check occurs later in [`0013_visit_commands.sql`](../../supabase/migrations/0013_visit_commands.sql) lines 250–258. An authenticated caller with a known entry ID, but no `queue.manage` capability, can make the definer function wait on or acquire a child lock before receiving `CV403`. Require capability before the new lock; retain the original function's entry check and receipt behavior.

## Scheduling review evidence

- **Lock order:** book, reschedule, check-in, transfer acceptance, queue transition and merge now acquire child locks before their own scheduling writes. Reschedule's prior body orders its two session locks by ID. Appointment arrival then locks its session; cancellation locks a session but does not take a child lock. Merge orders its two child locks by ID. I found no definite lock cycle in the inspected paths. An explicit two-session deadlock test across cancellation, merge and transition would be stronger evidence than static review.
- **Replay:** `scheduling_replay` verifies actor, command type and payload hash. Check-in replay precedes its newly added cancelled-session rejection, so a completed arrival can be replayed after later cancellation. It also precedes the new child lock. Book/reschedule check caller scope before replay, matching their original security posture. Merge and transfer require capability before replay. Their prior command bodies still own receipt finalization and audit.
- **Merge collisions:** same-session confirmed duplicate bookings are cancelled and audited before moving remaining usable bookings to the survivor. A `checked_in` duplicate with a conflicting survivor booking is rejected. Active ticket collisions and open encounters are rejected. The partial unique indexes on active appointments and tickets remain the final database guard. Completed/history rows intentionally remain on the alias child. No uncovered collision was proven by this read-only pass.
- **Effective-date inputs:** `evaluate_rules` rejects dose dates after `as_of`; `child_eval_inputs` excludes future dated doses and restricts holds by local effective start/resolution dates. Planned-dose checks use the proposed date. A future or historical persisted evaluation does not replace the present child program assignment. The implementation interprets undated doses as unresolved at every evaluation date and historical evaluations use today's current revision state; these are limits of date-based reconstruction, not evidence of a new regression.

## API/UI review evidence and limits

The shared API handler bounds the body before RPC construction; SMS callback verification precedes its privileged DB connection. Production URL and CSRF comparison use a canonical origin. Query integer parsing is strict. The public certificate verification page renders a distinct unavailable state when its RPC fails. Several server worklists now let RPC rejection reach the page error boundary, while the inbox null case above remains. The root layout reports a failed unread badge as unavailable, but its separate `safeViewer` catch still presents an anonymous shell during a context read outage; page-level access then determines the final state. No runtime browser, ingress, Supabase Auth, SMS provider, or full integration claim follows from this static inspection.
