# CVSRS database and business logic audit

Date: 2026-09-30. Scope: the 24 ordered SQL migrations, database adapter and RPC allowlist, worker/SMS/certificate paths, and `tests/db`. This is a static audit of the current working tree. `package.json` and several UI files were already modified; this audit did not change them. Findings below distinguish code-proven behavior from a concurrency scenario that still needs a two-session test.

## System map

- `0001` establishes organizations, profiles, clinics, live staff memberships, role/capability checks, audit logs and idempotent receipts. `0002` adds two-person staff grant/revocation commands. `0003`-`0005` implement child/guardian registry, enrollment, review/merge, QR and public/staff reads.
- `0006`-`0010` define clinical master data, immutable event/revision history, schedule rules and lifecycle, evaluation/credits, and outside-dose evidence. `0011` defines the append-only stock ledger and balance projection. `0012`-`0014` add sessions, appointments, queue, encounters and outbox. `0015`-`0016` add administration, exceptions and corrections.
- `0017` adds certificates, immutable PDF storage, messaging and outbox processing. `0018`-`0020` add reports, paper tallies, interclinic stock transfer, temperature logs and SMS consent/delivery. `0021`-`0024` add catch-up plans, check-ins, holds, follow-up, record transfer, reviewed content, audit search and operations status.
- The API uses [`src/lib/db/port.ts`](../../src/lib/db/port.ts) as an RPC allowlist. Production uses the caller's Supabase session in [`supabase.ts`](../../src/lib/db/supabase.ts); local mode switches to `authenticated` with synthetic JWT claims in [`local.ts`](../../src/lib/db/local.ts). Most tables have RLS enabled and no direct API-role table grants; public commands are `SECURITY DEFINER` functions with explicit capability/relationship checks.
- [`scripts/worker.ts`](../../scripts/worker.ts) and [`src/lib/worker/outbox.ts`](../../src/lib/worker/outbox.ts) process database outbox jobs, then send SMS through [`dispatch.ts`](../../src/lib/sms/dispatch.ts). Certificate rendering spans SQL commands and [`service.ts`](../../src/lib/certificates/service.ts).

## Findings

### P1 — historical schedule results can include future doses and today's holds (production; verified from code)

[`private.child_eval_inputs`](../../supabase/migrations/0007_schedule_engine.sql#L193) gathers every current verified dose and active hold without an as-of filter ([lines 196-211](../../supabase/migrations/0007_schedule_engine.sql#L196)). [`evaluate_rules`](../../supabase/migrations/0007_schedule_engine.sql#L73) accepts any matching dose without checking `d.don <= p_as_of`; [`evaluate_child`](../../supabase/migrations/0007_schedule_engine.sql#L278) exposes arbitrary `p_as_of` and persists the result. A dose dated October 1 can therefore mark a requirement `completed` in an evaluation dated September 1. A hold placed later can also mark that earlier evaluation as needing review. [`check_planned_dose`](../../supabase/migrations/0015_administration.sql#L24) uses the same unfiltered input when checking a backdated administration. Pass the as-of date into input collection, filter doses and holds using their effective dates, and reject/mark unresolved future dated evidence as appropriate. Add a historical before/after-dose test and a backdated administration test.

### P1 — reserved walk-in capacity can be exceeded without an overflow reason (production; concurrency scenario derived from code)

[`check_in`](../../supabase/migrations/0013_visit_commands.sql#L196) reads open-session walk-in capacity and counts used walk-in tickets in separate statements ([lines 226-231](../../supabase/migrations/0013_visit_commands.sql#L226)). It only locks the ticket counter later via [`allocate_ticket`](../../supabase/migrations/0012_visits.sql#L185). Two transactions can each read `used = capacity - 1`, pass, then serialize ticket allocation and both insert a ticket. The unique active-child index prevents duplicate children, not over-capacity. Lock a clinic/day capacity row before reading the count, or use an atomic allocation counter. Test two simultaneous different-child walk-ins for the final slot, including that the rejected/overflow path records a reason. The existing test checks sequential overflow in [`visits.test.ts`](../../tests/db/visits.test.ts#L246); simultaneous bookings are covered separately at [line 83](../../tests/db/visits.test.ts#L83).

### P1 — a cancelled session's appointment can still be checked in (production; verified from code)

[`cancel_session`](../../supabase/migrations/0013_visit_commands.sql#L38) intentionally keeps confirmed appointments and opens follow-up cases ([lines 51-59](../../supabase/migrations/0013_visit_commands.sql#L51)). [`check_in`](../../supabase/migrations/0013_visit_commands.sql#L219) validates the appointment is confirmed and dated today, but never checks `s.status`; it can create a queue entry for a cancelled session. Reject appointment check-in for closed/cancelled sessions, with a clear rebooking path. Add a test that cancels a same-day session then tries its confirmed appointment. The existing cancellation test checks cases/jobs but not arrival ([`visits.test.ts:194`](../../tests/db/visits.test.ts#L194)).

### P1 — merged child's existing appointments become unusable (production; verified from code)

[`merge_children`](../../supabase/migrations/0003_registry.sql#L735) moves relationships/enrollments and marks the duplicate merged ([lines 755-779](../../supabase/migrations/0003_registry.sql#L755)), but does not move or cancel its appointments. [`check_in`](../../supabase/migrations/0013_visit_commands.sql#L204) canonicalizes the requested child, then requires `appointment.child_id = canonical child` ([line 219](../../supabase/migrations/0013_visit_commands.sql#L219)); the old appointment fails even with its valid ID. [`my_appointments`](../../supabase/migrations/0013_visit_commands.sql#L179) checks guardian access against the appointment's old child ID after relationships have moved. Define whether to reassign or cancel/rebook these appointments during merge, preserving an audit trail and capacity. Add a merge-with-future-booking test covering guardian listing, cancel and check-in.

### P1 — guardian booking is not bound to the destination clinic's enrollment (production; verified from code)

[`can_book_for`](../../supabase/migrations/0012_visits.sql#L205) returns `online` as soon as the guardian has full access to the child; only the assisted staff branch checks `child_in_clinic` ([lines 238-244](../../supabase/migrations/0012_visits.sql#L207)). [`book_appointment`](../../supabase/migrations/0013_visit_commands.sql#L65) relies on that helper and can therefore book a child into a session at another clinic of the same organization where the child is not enrolled. The composite FK enforces organization, not enrollment. Require the destination clinic enrollment for both channels, or create a deliberate referral flow. Add a two-clinic guardian booking test. This also narrows the record-transfer booking race below.

### P1 — stock reconciliation repair can overwrite a concurrent ledger posting (production; concurrency scenario derived from code)

[`reconcile_stock`](../../supabase/migrations/0011_inventory.sql#L415) computes ledger/projection differences, then upserts the previously calculated ledger total into `stock_balances` ([lines 422-432](../../supabase/migrations/0011_inventory.sql#L422)) without locking the balance/ledger posting path. [`post_movement`](../../supabase/migrations/0011_inventory.sql#L181) and the [`apply_movement` trigger](../../supabase/migrations/0011_inventory.sql#L127) can post a movement between that read and repair; repair then sets the projection to the older total. Serialize repair against postings for the clinic or compare a movement watermark and retry. Add a two-session repair-vs-post test and rerun reconciliation afterward.

### P1 — report export audit can be bypassed by a granted RPC (production; verified from code)

The public report functions are granted to `authenticated` ([`0018` lines 226-235](../../supabase/migrations/0018_reports.sql#L226)). They take caller-controlled `p_export`; for example [`report_daily_activity`](../../supabase/migrations/0018_reports.sql#L74) audits only when `not p_export` ([line 103](../../supabase/migrations/0018_reports.sql#L103)). The API export route separately calls `record_report_export` before calling the report with `p_export: true` ([`export/route.ts` line 31](../../src/app/api/v1/clinics/[clinicId]/reports/[name]/export/route.ts#L31)). A user with `report.run` can directly invoke the granted report RPC with `p_export = true` and obtain the result without the export audit entry. Couple report generation and export audit in one database command, or audit every read regardless of flag. Add a direct-RPC audit test; current report tests exercise the separate export-record call at [`reports.test.ts:149`](../../tests/db/reports.test.ts#L149).

### P1 — certificate rendering can issue a PDF with an invalid verification token (production; concurrency scenario derived from code)

[`begin_certificate_render`](../../supabase/migrations/0017_certificates_messages.sql#L164) reads the pending certificate without a lock, rotates its token hash, and returns the token ([lines 167-174](../../supabase/migrations/0017_certificates_messages.sql#L167)). Two renderers can both pass the pending check; the second rotation supersedes the token already printed by the first. [`store_certificate_pdf`](../../supabase/migrations/0017_certificates_messages.sql#L176) verifies only PDF header/checksum and pending status, not that the PDF contains the currently hashed token ([lines 187-200](../../supabase/migrations/0017_certificates_messages.sql#L187)). The first renderer can then store a PDF whose QR never verifies. Add a render generation/token claim, serialize begin/store, and bind storage to the generation. The current certificate test checks sequential token rotation at [`certificates.test.ts:125`](../../tests/db/certificates.test.ts#L125), not concurrent rendering.

### P2 — paper reconciliation export ignores small-cell suppression (recommended; verified from code)

[`report_paper_reconciliation`](../../supabase/migrations/0018_reports.sql#L187) accepts `p_export` but returns `paperCount`, `systemCount` and `difference` directly ([lines 195-207](../../supabase/migrations/0018_reports.sql#L195)). [`export/route.ts`](../../src/app/api/v1/clinics/[clinicId]/reports/[name]/export/route.ts#L33) requests `p_export: true` for every report. Thus a configured positive small-cell threshold has no effect on a product/day paper tally, despite the migration's export policy ([`0018` lines 1-7](../../supabase/migrations/0018_reports.sql#L1)). Apply suppression consistently to every sensitive count and dependent difference, or explicitly exclude this report from export pending privacy review. Existing suppression tests cover the vaccination count and product report, not paper reconciliation ([`reports.test.ts:134`](../../tests/db/reports.test.ts#L134)).

### P2 — SMS delivery completion has no claim-generation check (recommended; concurrency scenario derived from code)

[`claim_sms`](../../supabase/migrations/0020_sms_preferences.sql#L187) requeues expired `sending` messages and increments `attempt_count` on a new claim. [`mark_sms`](../../supabase/migrations/0020_sms_preferences.sql#L202) accepts only the message ID and checks `status = 'sending'`, so a delayed first worker can mark the message `sent` or `retry` after a second worker has reclaimed it. [`dispatchSms`](../../src/lib/sms/dispatch.ts#L15) performs the provider call outside the transaction, making lease expiry possible. Return a claim token/attempt from `claim_sms`, require it in `mark_sms`, and ensure provider idempotency by message ID. Existing SMS tests cover concurrent initial claims and retry, not expired lease/stale completion ([`sms.test.ts:132`](../../tests/db/sms.test.ts#L132)).

### P2 — certificate PDF trust boundary relies on caller behavior (recommended; verified from code)

Any holder of `certificate.issue` can directly call the granted [`store_certificate_pdf`](../../supabase/migrations/0017_certificates_messages.sql#L176) RPC after beginning a render. SQL checks a `%PDF-` prefix and SHA-256 of supplied bytes ([lines 187-193](../../supabase/migrations/0017_certificates_messages.sql#L187)); it does not prove that the bytes were produced from the frozen certificate snapshot. The app's [`renderAndStore`](../../src/lib/certificates/service.ts#L35) follows the intended renderer path, but database grants do not enforce it. If certificate contents must be tamper resistant even from a staff RPC client, move PDF storage behind a server-only credential/service or render deterministically in a trusted worker with a bound snapshot/token digest. Test a direct RPC upload of a different valid PDF to define the intended trust policy.

### P3 — record transfer can race a new booking at the old clinic (future hardening; concurrency scenario derived from code)

[`accept_record_transfer`](../../supabase/migrations/0023_record_transfer.sql#L111) locks the transfer, closes enrollment, then loops over currently confirmed old-clinic appointments ([lines 123-135](../../supabase/migrations/0023_record_transfer.sql#L123)). [`book_appointment`](../../supabase/migrations/0013_visit_commands.sql#L65) locks the session but checks enrollment through `can_book_for` before inserting; transfer acceptance does not acquire that session lock or a common child/enrollment lock. A booking can pass its access check while acceptance is in progress and insert after the cancellation loop, leaving a confirmed booking at a clinic that has lost the child. Serialize transfer and booking on the child/enrollment row, then add an interleaving test.

### P2 — multiple confirmed sessions for one child and date are permitted (recommended; verified from code)

[`appointments_one_active_uq`](../../supabase/migrations/0012_visits.sql#L80) is unique only on `(child_id, session_id)` and [`book_appointment`](../../supabase/migrations/0013_visit_commands.sql#L81) checks only the same session. The same child may reserve several sessions for the same clinic/day, consuming multiple online slots. If repeat visits in one day are supported, require a distinct service or explicit staff decision; otherwise enforce one active appointment per child/clinic/service date with a lock or schema field/index. Add a cross-session booking test. This is a policy decision before implementation, not evidence of a duplicate vaccination.

## Verified controls and coverage gaps

- Staff checks use live membership, clinic status, profile status and configurable MFA ([`0001` lines 321-367](../../supabase/migrations/0001_foundation.sql#L287)); grant approval requires a different requester, approver and grantee ([`0002` lines 52-83](../../supabase/migrations/0002_staff_access.sql#L52)). Guardian clinical reads require an active full-access relationship ([`0003` lines 247-253](../../supabase/migrations/0003_registry.sql#L247)). Direct table access is largely revoked and RLS enabled. These are strong design controls, but local tests use synthetic `aal2` claims and do not validate real Supabase Auth/MFA or PostgREST behavior ([`local.ts`](../../src/lib/db/local.ts#L7)).
- Booking locks the session for capacity ([`0013` lines 72-85](../../supabase/migrations/0013_visit_commands.sql#L72)); tests include simultaneous bookings ([`visits.test.ts:83`](../../tests/db/visits.test.ts#L83)). Stock issue and ledger projection are same-transaction and row locked ([`0011` lines 127-159](../../supabase/migrations/0011_inventory.sql#L127)); inventory tests include concurrent issue ([`inventory.test.ts:276`](../../tests/db/inventory.test.ts#L276)). Administration serializes on encounter, creates immutable revisions and posts stock in one transaction ([`0015` lines 79-141](../../supabase/migrations/0015_administration.sql#L79)).
- Outbox jobs use `FOR UPDATE SKIP LOCKED` and bounded retry ([`0017` lines 388-413](../../supabase/migrations/0017_certificates_messages.sql#L388)); SMS initial claims also use `SKIP LOCKED` ([`0020` lines 187-200](../../supabase/migrations/0020_sms_preferences.sql#L187)). Their tests do not exercise process death/lease expiry or the race above. Certificate tests cover token rotation and PDF checksum/size, but not two concurrent renderers or content binding.
- Missing coverage for historical as-of dose/hold filtering, concurrent final-slot walk-ins, cancelled-session arrival, merge with active bookings, guardian booking at an unenrolled clinic, cross-session duplicate reservations, reconciliation repair vs posting, direct report RPC audit bypass, small paper export cells, certificate render race, stale SMS worker completions, and booking during record transfer.

## Validation performed

Static inspection and cross-reference of migrations, API adapters/routes, worker paths and database test cases; `git status --short` confirmed preexisting modified UI/package files and this new audit file. No database test was run: [`tests/db/global-setup.ts`](../../tests/db/global-setup.ts#L1) calls `reset("cvsrs_test")`, so invoking `npm run test:db` would reset a database. No database, product code, or user data was changed by this audit. Findings labeled concurrency scenario need the proposed two-session tests to establish runtime behavior under this deployment.
