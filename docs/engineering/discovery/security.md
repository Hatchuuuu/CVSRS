## Findings

### SEC-01 — Default rate-limit identity is one global bucket per route, applied before authentication: one anonymous client can lock every user out of sign-in, certificate checks, waiting-room displays and clinic queue actions
- Priority: P1
- Class: Reproduced defect
- Location: `src/lib/security/rate-limit.ts:27-34` (`identity = header ? … : "global"`; route path with every UUID replaced by `:id`); `src/lib/api/handler.ts:45-49` (limit runs before `rpc.session()`); `src/lib/auth/request.ts:61-65` (`auth/sign-in` 30/min, `auth/sign-up`); `src/app/verify/[token]/page.tsx:28` and `src/app/api/v1/verify/[token]/route.ts:5` (30/min); `src/app/api/v1/clinics/[clinicId]/queue/display/route.ts:4` (60/min) polled every 5 s by `src/app/display/[clinicId]/board.tsx:16-26`; `src/app/api/v1/guardian-links/route.ts:5` (5/min); `src/app/api/v1/webhooks/sms/route.ts:17` (300/min, before signature check); `.env.example:37-39`; `README.md:72`.
- Evidence: `.local/audit-scratch/security/global-bucket.unit.ts`, 4/4 passing against current code with the documented default (`CVSRS_TRUSTED_CLIENT_IP_HEADER=` blank):
  1. `requestLimitKey` for `/api/v1/clinics/<clinicA>/queue/display` from 10.0.0.1 and `/api/v1/clinics/<clinicB>/queue/display` from 10.9.9.9 are both `global|/api/v1/clinics/:id/queue/display`.
  2. 30 wrong-password `POST /auth/sign-in` from one client, then a different user's sign-in → **429**.
  3. 60 display polls for clinic A (= five screens at 12 polls/min), then clinic B's display → **429** (board shows stale data for every clinic).
  4. 60 unauthenticated `POST /api/v1/clinics/<A>/queue/call-next` (no session, Origin header set by the script) → clinic B's next call-next → **429**. A non-browser client can always send a matching `Origin`, so the CSRF check does not stop this.
  The Redis path uses the same key (only hashed), so production behaves identically to this in-memory reproduction.
- Impact: Any anonymous internet client can, for the cost of ~1 request/second per route, deny sign-in to all guardians and staff nationwide, block every certificate verification, freeze every waiting-room display, and block queue/recording mutations at every clinic. Even with no attacker, normal multi-clinic load exceeds the shared ceilings (5 display screens; >60 `call-next`/minute across all clinics; 5 guardian-link requests/minute for the whole country). The SMS webhook bucket can be exhausted before signature verification, making the provider's genuine receipts fail. README calls the blank setting "needs capacity validation"; the consequence is an essential-flow outage, not a capacity tuning question.
- Root cause: The only client dimension is an optional trusted header; when it is absent the key collapses to the route pattern. Authenticated routes never key on the authenticated user.
- Solution: (1) Two-tier keys in `api()`: keep a pre-auth limit keyed on a trusted client address, and add a post-auth limit keyed on `session.userId` (and clinic id from the path) for authenticated routes. (2) In production, refuse to start (ConfigError, same as `CVSRS_PUBLIC_URL`) unless a trusted client-address source is configured (platform-overwritten header such as the hosting provider's documented real-IP header), or explicitly opt into `CVSRS_RATE_LIMIT_GLOBAL_ONLY=1` with a much higher, documented ceiling. (3) Sign-in: key on `(client address, lower(email))` plus a high global ceiling; never a 30/min deployment-wide bucket. (4) SMS webhook: verify the HMAC before charging the bucket, or key the bucket on signature validity. (5) Display: key on clinic id + client address. Also verify (external) that Supabase Auth's own per-IP limits are configured for server-side `signInWithPassword`, since Auth sees the web server's IP for every user.
- Acceptance: With the production configuration, requests from two different client addresses never share a bucket; two authenticated users never share a post-auth bucket; 31 failed sign-ins from client X do not change client Y's outcome; display polling at 50 clinics stays below limits; an unsigned webhook flood does not 429 a correctly signed callback.
- Verification: Promote `global-bucket.unit.ts` into `tests/unit/` with the assertions inverted (expect no 429 for the victim), plus a production-mode test that `getConfig()`/`limitRequest` refuses to run without a trusted client-address source.

### SEC-02 — Sign-out reports success but leaves the Supabase session cookie in the browser when the token refresh fails
- Priority: P2
- Class: Reproduced defect
- Location: `src/app/auth/sign-out/route.ts:13-26`
- Evidence: `.local/audit-scratch/security/signout.unit.ts` uses the real `@supabase/ssr` 0.12.7 and `@supabase/auth-js` 2.117.2. Cookie jar holds `sb-project-auth-token` whose access token is expired (normal after 1 h idle); `fetch` fails (Auth outage / network blip). Output: `status 303 location / fetch calls 8 cookies left [ 'sb-project-auth-token' ] set calls []`, after ~25 s of retries. auth-js `_signOut` (`GoTrueClient.js:3433-3436`) returns `{ error }` without `_removeSession()` when loading/refreshing the session fails; the route ignores the returned error and always redirects to `/` as if signed out.
- Impact: On a shared clinic computer, a staff member who signs out after being idle (expired access token) during an Auth/network disruption sees the normal signed-out landing page, but the refresh token remains in a 400-day cookie (see SEC-03). When connectivity returns, the next person at the terminal is silently signed in as that staff member (DB still demands aal2 for staff capabilities only if the stored session was aal1; an aal2 session restores full clinic access). The request also blocks ~25 s.
- Root cause: The sign-out route treats `supabase.auth.signOut()` as infallible and relies on it to clear cookies.
- Solution: Always expire every Supabase auth cookie in the response, independent of the SDK result: iterate `jar.getAll()` and set `maxAge: 0` for names matching the storage key (`sb-<ref>-auth-token`, its `.0`, `.1`… chunks and `-code-verifier`). Call `signOut()` with a short timeout; if it returns an error, still clear locally and show "Signed out on this device; we could not end your other sessions — try again" instead of the plain landing page. Keep the local-dev branch unchanged.
- Acceptance: With Auth unreachable and an expired access token, `POST /auth/sign-out` responds within the timeout, the response contains `Set-Cookie` expiring every `sb-*-auth-token*` cookie, and the user is told revocation did not complete.
- Verification: Move `signout.unit.ts` into `tests/unit/sign-out.test.ts` with inverted expectations; keep the existing same-origin tests.

### SEC-03 — Session cookies are 400-day persistent, not `Secure`, not `HttpOnly`; no idle lock, absolute session lifetime, or step-up reauthentication required by the blueprint
- Priority: P2
- Class: Missing required behavior (cookie attributes reproduced)
- Location: no `cookieOptions` at any `createServerClient`/`createBrowserClient` site: `src/app/auth/sign-in/route.ts:26-28`, `src/app/auth/sign-up/route.ts:27-29`, `src/app/auth/callback/route.ts:32-38` (comment on line 7 says "stored in HTTP-only cookies" — false), `src/proxy.ts:31-41`, `src/lib/db/supabase.ts:10-22`, `src/lib/client/supabase-browser.ts:9`. Defaults: `node_modules/@supabase/ssr/dist/main/utils/constants.js:4-11`. Requirement: `docs/specification/CVSRS-Final-Master-System-Blueprint.md:875-885` (§32: Secure/SameSite cookies, clinic-approved inactivity locking and absolute session lifetime, reauthentication for role changes, bulk exports, certificate revocation and sensitive account recovery; shared clinic computer → idle lock, clean logout).
- Evidence: `.local/audit-scratch/security/cookie-flags.unit.ts` drives the production sign-in route with the real SDK: `{"name":"sb-project-auth-token","options":{"path":"/","sameSite":"lax","httpOnly":false,"maxAge":34560000}}` (400 days, no `secure`). `grep -ri "idle\|inactiv\|reauth" src` finds no idle lock or reauthentication. `src/app/account/reset-password/reset-password-form.tsx:14-41` lets any signed-in session change the password with no current-password/nonce/fresh-MFA check. `src/app/clinic/[clinicId]/reports/[name]/export/route.ts`, `…/certificates/[certificateId]/revoke/route.ts`, `…/staff/route.ts` have no step-up. Password floor is 8 server-side at sign-up (`sign-up/route.ts:23`) but 12 client-side only at reset (`reset-password-form.tsx:54-55`).
- Impact: Closing the browser on a shared clinic terminal does not end a staff session; the refresh token persists for 400 days (bounded only by whatever the Supabase project's session settings are). Tokens are readable by any script that ever executes on the origin (mitigated today by the nonce CSP). Without `Secure`, the cookie is eligible for plain-HTTP requests on first visit before HSTS is cached. Someone at an unattended signed-in terminal can export reports, revoke certificates, change the password and request staff grants without proving identity again.
- Root cause: SDK defaults accepted; blueprint §32 session controls not implemented.
- Solution: One shared cookie-options factory used at all six sites: `{ path: "/", sameSite: "lax", secure: production, maxAge: <work-shift seconds, operational policy> }` (or omit `maxAge` for a browser-session cookie on staff terminals). HttpOnly cannot be enabled while the browser SDK (MFA panel, reset form) reads the session — document this per §32 and fix the callback comment. External: enable Supabase session time-box and inactivity timeout and "Secure password change". Application: staff idle lock (client timer that calls `/auth/sign-out`), and server-side step-up for export/revoke/staff-grant/password change (e.g. require a JWT `iat`/MFA `amr` timestamp within N minutes, re-checked in the route or the SQL function). Align the password floor (server-enforced in Supabase Auth policy).
- Acceptance: Production sign-in `Set-Cookie` has `Secure`, the agreed `Max-Age` (or none), `SameSite=Lax`, `Path=/`; an idle staff terminal is signed out after the agreed period; export/revoke/grant/password change are refused with a step-up prompt when the last authentication is older than the agreed window.
- Verification: Promote `cookie-flags.unit.ts` with corrected expectations; unit tests for the step-up guard; Supabase settings recorded as external evidence.

### SEC-04 — Rate-limit store outage degrades to per-process memory for every scope, including anonymous abuse-sensitive routes (decision on prior-audit item L3)
- Priority: P3
- Class: Inspection risk
- Location: `src/lib/security/rate-limit.ts:63-93`; `README.md:72` ("missing/unavailable configuration fails closed"); `tests/unit/shared-rate-limit.test.ts` ("fails closed on shared store errors" covers only failures 1-4); `docs/implementation/known-limitations.md:9` (L3).
- Evidence (code, current tree): failures 1-4 throw 503 (fail closed). On the 5th, `openUntil = now + 15 s`; while open, every scope uses `hit("degraded:"+key, max(5, floor(limit/2)))` in the process-local `Map`. After 15 s the next request probes the store (up to 2.5 s timeout), fails, `consecutiveFailures` is already ≥ 5, so the circuit re-opens: steady state during an outage is "degraded, one 503 per 15 s per instance". There is no per-scope choice.
- Impact / decision: Degradation is **acceptable** for authenticated reads and mutations (the database authorizes every call; availability matters more than precise throttling). It is **not acceptable** for anonymous, abuse-sensitive scopes — `auth/sign-in`, `auth/sign-up`, `verify` page/API, `guardian-links`, `qr/resolve`, `sms-webhook` — because on a horizontally scaled or serverless host the effective ceiling becomes `instances × limit/2`, and an attacker who can exhaust the store's request quota (every request issues an EVAL) can force this mode. Severity is limited (half limits per instance; Supabase Auth has its own limits), hence P3. The README statement is inaccurate.
- Root cause: Single global circuit with one degradation policy.
- Solution: `limitRequest(key, limit, windowMs, { onStoreFailure: "closed" | "degrade" })`; pass `"closed"` from `authRateLimit`, the verify route/page, guardian-links, QR resolve and the SMS webhook; keep `"degrade"` as the default for authenticated API routes. Correct README and rename the unit test.
- Acceptance: With the circuit open, `auth/sign-in` returns 503 (not a degraded allow); an authenticated GET still degrades.
- Verification: Extend `tests/unit/shared-rate-limit.test.ts` with both policies.

### SEC-05 — `merge_children` checks visit/queue/booking state and locks rows for caller-supplied child IDs before the clinic/organization ownership check (cross-org state oracle)
- Priority: P3
- Class: Reproduced defect
- Location: `supabase/migrations/0025_scheduling_integrity.sql:100-123` (wrapper: `require_capability` → `scheduling_replay` → `select … for update` and `CV409` conflict checks on `p_survivor`/`p_duplicate`, then `merge_children_prev`, whose ownership check is in `0003_registry.sql:735+`).
- Evidence: `.local/audit-scratch/security/idor.dbtest.ts` ("merge_children wrapper state oracle"): a clinic-A lead with `review.resolve` calls `merge_children(op, clinicA, childA, childC)` where `childC` belongs to a **different organization** and has an open encounter → `CV409` "finish active visits before merging records" (passed verbatim to the API client by `src/lib/api/errors.ts:67`); the same call for a foreign child without an open visit → `CV404`. The wrapper also takes `FOR UPDATE` locks on the foreign rows before rejecting.
- Impact: A reviewer can learn whether a known child UUID anywhere in the system currently has an open visit, active queue ticket or checked-in booking, and can briefly lock other organizations' child rows. Requires knowing random v4 UUIDs, so low.
- Root cause: The wrapper added in 0025 runs its pre-checks before delegating ownership validation to the renamed `_prev` function.
- Solution: New forward migration redefining `public.merge_children` to resolve both children with `organization_id = v_org` and `private.child_in_clinic(…, p_clinic_id)` (raise CV404 otherwise) before any lock or conflict check.
- Acceptance: The call with a foreign-clinic/foreign-org child returns CV404 regardless of that child's visit/queue/booking state, and takes no lock on it.
- Verification: Port the scratch test into `tests/db/registry.test.ts`.

### SEC-06 — Configuration error text is returned to anonymous clients
- Priority: P3
- Class: Reproduced defect
- Location: `src/lib/db/index.ts:16` (`new AppError("misconfigured", 503, e.message)`), messages in `src/lib/env.ts:30-59`.
- Evidence: `.local/audit-scratch/security/config-leak.unit.ts`: `GET /api/v1/clinics` (public) with a non-loopback `CVSRS_LOCAL_DB_URL` returns `503 {"error":{"message":"local-dev mode only accepts a loopback database"}}`. Other messages expose variable names (`CVSRS_PUBLIC_URL`, `NEXT_PUBLIC_SUPABASE_*`).
- Impact: Minor information disclosure about deployment configuration during a misconfiguration window; inconsistent with `errors.ts` "internals never leave the server".
- Solution: Use `safeMessage("misconfigured")` in the response and log `e.message` server-side with the request id.
- Acceptance: Misconfigured responses carry only "The service is not configured."
- Verification: Promote the scratch test with the inverted expectation.

## Checked and found sound (no finding)

- **Demo / local identity isolation (scope 1).** Decision path: `getConfig()` prefers Supabase when both public vars are set; local-dev requires a loopback `postgresql://` URL and is refused when `NODE_ENV=production`; persona selection (`src/lib/auth/demo.ts:10-16`) additionally requires `isDemoDatabase()` (DB `private.settings.demo_mode = true`) and is limited to nine reserved emails with `cvsrs_demo_persona` metadata (`src/lib/db/local.ts:70-119`); the local session (`local.ts:27-31`) re-checks the demo database on every call, so `local-dev` against a non-demo DB (e.g. `db:setup`) yields no session (fail closed). Inspected the current `next build` output (`.next/server/chunks`, BUILD_ID 21:11 today): in a production build `selectDemoPersona` compiles to an unconditional `throw` and the in-memory rate-limit branch is removed, because `process.env.NODE_ENV` is inlined at build time. Only `getConfig().production` reads the runtime `NODE_ENV` (via `{...process.env}`), so `next start` with a non-production runtime `NODE_ENV` would skip the `CVSRS_PUBLIC_URL` check and accept `local-dev` mode, but every downstream guard still fails closed (no demo session, origin check requires `CVSRS_PUBLIC_URL`, proxy requires Supabase). Missing Supabase config in production → proxy 500 and `getConfig` ConfigError → 503. No bypass, persona selection or fake success found. `CVSRS_DEMO_MODE` only controls watermark text.
- **Auth lifecycle.** Sign-in/sign-up: same-origin check, bounded (16 KB) duplicate-key-safe field parser, uniform credential errors, server-generated redirects only. PKCE callback: canonical origin in production, request-origin mismatch → 400, `next` allowlisted to three paths (`src/lib/auth/redirect.ts`), provider error → `/sign-in?auth=link-error`. Sign-up `emailRedirectTo` uses `req.url` origin, but in production `isSameOrigin` has already pinned that origin to `CVSRS_PUBLIC_URL`. Recovery request returns the same message for unknown emails. MFA: staff capabilities require `aal2` in `private.mfa_ok()` (`0001_foundation.sql:292-294`), verified in scratch DB test (aal1 lead → CV403). Sign-out is POST + same-origin (but see SEC-02).
- **API boundary.** `api()` enforces same-origin on every non-GET/HEAD, UUID route params, Idempotency-Key, bounded UTF-8 body (1 MB default, 5 MB schedule import), Zod validation, auth by default, safe error envelope; `fromDbError` exposes only authored CV409/CV422 text. Custom routes: certificate download (GET, session + `get_certificate_pdf` authz, nosniff, private no-store), report export (GET, session + `report_*`→`report_org` capability, CSV formula neutralization in `src/lib/reports/csv.ts:5`), SMS webhook (HMAC-SHA256 with `timingSafeEqual`, separate `CVSRS_SMS_WEBHOOK_DB_URL` role with only `record_sms_event`), verify (public, 64-hex token, no PII), health (static), auth routes (own same-origin checks). No GET handler performs a state change other than audit rows. Origin check requires `Origin` in production.
- **Object authorization (scope 4).** Grant inventory on a freshly migrated DB: anon can execute only `list_public_clinics`, `public_queue_display`, `verify_certificate`; 153 functions executable by `authenticated`, all `SECURITY DEFINER` with pinned `search_path`; no public table without RLS; table grants limited to SELECT on 6 RLS tables + column UPDATE on `profiles(display_name, locale)`; `_prev` helpers not executable. Because the publishable key lets any authenticated user call these functions directly through PostgREST, the app's RPC allowlist, rate limits and Zod schemas are not security boundaries; the SQL checks are, and the scan found an authorization helper (`has_capability`/`require_capability`/`require_any`/`inventory_org`/`report_org`/`guardian_has_full_access`/`can_book_for`/own-row predicate) in every non-public function. Store of certificate PDFs is bound by a server-only HMAC attestation (`0027`). Sampled routes and their SQL (route → function → check): children/:id/history → `guardian_child_history` (full access); children/:id/qr → `issue_qr_pass` (full access or `child.register`+enrollment); children/:id/certificates → `guardian_list_certificates`; children/:id/record-transfers GET/POST → `my_record_transfers` / `request_record_transfer_guardian`; record-transfers/:id/cancel → `cancel_record_transfer_guardian` (transfer's child, path childId ignored safely); appointments/:id/cancel → `cancel_appointment` (`can_book_for`); appointments POST → `book_appointment`; clinics/:c/children/:id GET/PATCH → `staff_get_child` / `update_child_identity`; …/history → `list_child_history`; certificates/:id/revoke → `revoke_certificate` (cert must match clinic+org); certificates/:id/retry → `begin_certificate_render` (cert's clinic); staff/:m/approve → `approve_staff_membership` (membership's clinic, two-person); staff POST → `find_profile_for_grant` + `request_staff_membership`; stock/lots/:id/ledger → `list_lot_ledger` (location clinic filter); audit → `search_audit`; me/messages/read → `mark_messages_read` (own rows); guardian-links → `request_guardian_link`; qr/resolve → `resolve_qr`; merges → `merge_children` (SEC-05); followup → `list_followup_worklist`/`log_followup_attempt`; contact-preferences → `set_contact_preferences` (SMS opt-in requires clinic-verified phone); reports/:name → `report_*`. Scratch DB test confirmed denials for mismatched pairs (clinic A id + clinic B child; clinic B id by clinic-A staff; foreign-org staff; unrelated guardian; aal1 staff).
- **Secrets/config.** No service-role key in `src/`; `.env.example` documents it must never be set; `server-only` on all modules reading server secrets except `src/lib/security/origin.ts`, `src/lib/sms/index.ts`, `src/lib/worker/outbox.ts` (they read no secret values that reach client bundles; worker URL is only used server-side; production web process never starts the poller, `outbox.ts:44`). Worker and webhook roles (`0028_runtime_roles.sql`) are NOLOGIN groups with execute on only their functions. Certificate render secret is server-only and mirrored in a private table with no grants.
- **Unsafe rendering / SSRF / CSP.** No `dangerouslySetInnerHTML`, `innerHTML`, markdown rendering, `eval`/`new Function` in `src/`. Only outbound `fetch` with a configured URL is the rate-limit store (`redirect: "error"`, HTTPS-only check). No file uploads. CSP: per-request nonce + `strict-dynamic` in production, `frame-ancestors 'none'`, `form-action 'self'`, `object-src 'none'`; static headers include HSTS, nosniff, `X-Frame-Options: DENY`, COOP/CORP, `Referrer-Policy: same-origin` (keeps verify tokens out of referrers).
- **Dependency audit.** `npm audit --omit=dev --offline` printed "found 0 vulnerabilities" but cannot fetch advisory data offline; treat as **not performed**, not as a clean result.
